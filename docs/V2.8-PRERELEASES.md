# v2.8 prerelease qualification

The user requested one prerelease per feature increment. Only an explicit later
instruction from the user may promote the completed track to stable **v2.8.0**.
Passing CI or finishing every beta does not authorize stable publication or
production deployment. Keep v2.7.0 selected as GitHub's latest stable release.
Do not include the separate v3 commercial/team branch in this track.

| Prerelease | Feature increment | Required checks |
| --- | --- | --- |
| v2.8.0-beta.1 | Reflect and reviewed project briefs | Citation rejection, budgets, isolation, stale sources, real local model |
| v2.8.0-beta.2 | Reviewed consolidation | Source quotations, originals/provenance preserved, stale approvals, repeat approvals |
| v2.8.0-beta.3 | Retrieval decay | Explainable priority adjustment, no content deletion, current/historical behavior |
| v2.8.0-beta.4 | Searchable archival | Explicit archive/restore, search controls, isolation and stale briefs |
| v2.8.0-beta.5 | Brief refresh for review | Explicit rebuild, immutable previous snapshots, changed evidence and project isolation |

Each increment is cumulative. Publish only after its backend, web, mobile,
Docker, disaster-recovery and CodeQL checks pass. Mark every GitHub release as a
**prerelease**, never as latest. Keep tags immutable and record the tested commit
and validation in its release notes. Fixes within an unreleased increment do not
create another feature version.

Before stable promotion: test the cumulative build against an isolated populated
database, verify migrations and rollback, complete user acceptance, then wait for
the user's explicit instruction. Native mobile distribution and Gmail retain
their separate qualification gates.
