# Engram v2.8.0 rollout

The stable release includes the thirteen cumulative feature increments documented in
[Memory lifecycle](MEMORY-LIFECYCLE.md). Native mobile distribution and Gmail retain
their separate qualification gates. The v3 commercial/team branch is excluded.

## Upgrade from v2.7.0

1. Save the current PostgreSQL dump, object-store backup, application images, environment,
   Compose files and host-specific overrides in a protected rollback directory.
2. Restore the database dump into an isolated PostgreSQL instance. Apply migrations
   013_project_briefs, 014_memory_archival, 015_cluster_review, 016_memory_pinning and
   017_lifecycle_undo in order with `psql -v ON_ERROR_STOP=1`. Verify source fingerprints
   and counts, then repeat the migrations to check idempotence.
3. Build application images from the exact release commit. Preserve host-specific
   configuration, routing, secrets, storage volumes and Ollama settings.
4. Stop API, worker and connector scheduler. Take a final database backup. Apply the
   five migrations in order, then recreate API, worker, scheduler, web and DR monitor.
5. Verify the public health/OpenAPI version, login, project isolation, API-key/MCP
   access, Ask, Reflect and brief freshness, pinning, archival and undo. Remove all
   temporary qualification data and compare retained source counts.

Fresh Compose installations initialize all migrations automatically. Existing databases
need explicit migration; mounting initialization files does not upgrade populated volumes.

## Behavior and rollback

Pins remove age penalties, not validity, access checks or query relevance. Archival is
reversible and distinct from deletion. Quick undo covers actions recorded after the
upgrade, up to seven days/50 recent actions. Newer edits block undo. Consolidation undo
archives the generated summary; source memories, provenance and the review record stay.

Retain pre-upgrade application images and sources. The migrations are additive, so the
previous application can run with the extra tables/columns left in place. Before reverting,
review any archived memories created under v2.8: older applications do not enforce the
new archival/pinning controls. A full database restore discards post-backup writes and
requires a separate deliberate recovery decision; code rollback does not restore a dump.

- 67 backend tests passed against isolated PostgreSQL and Redis, including project/scope
  boundaries, stale writes, exact quotations, history, pinning and audited lifecycle undo.
- Real local Ollama checks covered bounded retrieval, three-source reviewed consolidation,
  point-in-time evidence and missing knowledge-gap questions.
- A production backup with 672 memories and 1,890 documents restored into isolated
  PostgreSQL; migrations 013–017 applied twice without changing source fingerprints or
  counts. These are qualification snapshot counts, not quotas or permanent live counts.
- GitHub backend, web, mobile, Docker, DR and CodeQL checks are required for promotion.
  Final deployment verification and rollback artifacts are recorded on the deployment host.
